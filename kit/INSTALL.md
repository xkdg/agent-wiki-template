# Установка и обновление кита — инструкция для агента

Любой агент с доступом к shell и git (Claude Code, облачная сессия, Cowork, Cursor, Codex) может
развернуть или обновить кит по этой инструкции. Плагин `agent-wiki` делает то же через
`/agent-wiki:init`, `/agent-wiki:sync`, `/agent-wiki:upstream` — это удобство, не условие.

Кит — это две части:
- **файлы проекта** — `template/` по списку `kit/MANIFEST`: ядро (`core`) и заготовки (`seed`);
- **плагин** `plugin/` — роли субагентов и общие скиллы. Ставится на аккаунт или машину один раз
  и обновляется сам (см. `README.md §Установка`). В проект не копируется.

---

## Получить кит

Нужен **полный** клон (не `--depth 1`): `sync` достаёт из истории прошлую версию ядра.

```
git clone https://github.com/xkdg/agent-wiki-template <каталог-кита>
```

Клон уже есть — обновить: `git -C <каталог-кита> fetch origin && git -C <каталог-кита> checkout --detach origin/main`.
Версия, которую ставит скрипт, — текущий `HEAD` клона; другая — флагом `--ref <коммит|тег>`.
Python — `python` или `python3`, что есть в системе (нужен 3.8+).

---

## init — новый проект

1. Убедиться, что это корень проекта (git-репозиторий или каталог, который им станет). Есть
   `wiki/.kit-version` — проект уже развёрнут, нужен `sync`.
2. Уже есть `CLAUDE.md` или `wiki/` без `wiki/.kit-version` — это не init, а §Миграция.
3. `python <каталог-кита>/kit/kit.py init --project <корень>`.
   Скрипт создаёт файлы из `MANIFEST`, существующие не трогает, пишет `wiki/.kit-version`.
4. Заполнить заготовки — **с владельцем, не выдумывая**:
   - `wiki/INDEX.md §Проект` и `§Карта кода` — черновик по коду и README, затем показать владельцу;
   - `wiki/context/QUICK_REF.md §Границы` — инварианты называет владелец; из кода — только
     кандидаты на подтверждение;
   - `§Области ADR` — правая колонка под проект, неприменимое — `—`;
   - пустой проект — заготовки остаются с курсивом-подсказками до первой задачи, это нормально.
5. Не коммитить без согласия владельца. Сообщить, что `CLAUDE.md` подтянет вики в следующей
   сессии или после `/clear`.

---

## sync — обновить ядро

1. `python <каталог-кита>/kit/kit.py sync --project <корень> --dry-run` — посмотреть план.
2. Без `--dry-run` — применить. Скрипт по каждому файлу ядра сравнивает три состояния: каким он
   был в версии кита проекта (база), каким стал в проекте и каким стал в ките.
   - в проекте не правили → тихо обновляется;
   - совпадает с новой версией → без изменений;
   - правили в проекте → **конфликт**: скрипт печатает оба diff и не сдвигает версию.
   Заготовки (`seed`) не трогаются никогда; новые заготовки, которых в проекте нет, создаются.
3. Конфликтов нет — `wiki/.kit-version` сдвинут, готово. Есть — §Конфликты.
4. Показать владельцу итог: что обновилось, что осталось конфликтом и как разрешено. Не коммитить
   без согласия.

### Конфликты

Файл ядра правили в проекте — значит, это одно из трёх, и решает владелец:
- **проектное, попавшее в ядро** (правило работы с продом, договорённость о командах) — перенести
  в `wiki/context/QUICK_REF.md` или в личный `~/.claude/CLAUDE.md`, файл ядра взять из кита;
- **общее улучшение** — оставить пока как есть и предложить в кит (§upstream); после того как оно
  попадёт в кит, следующий sync совпадёт и конфликт уйдёт сам;
- **устаревшая локальная правка** — взять версию кита.

Взять версию кита для файла: `python <каталог-кита>/kit/kit.py take --project <корень> --path <путь> --ref <новый коммит>`
(сохраняет CRLF, если файл был с ним; `--path` можно повторять).

Разрешив все конфликты: `python <каталог-кита>/kit/kit.py stamp --project <корень> --ref <новый коммит>`
(команду с нужным коммитом печатает sync).

## Миграция — проект, развёрнутый старым шаблоном (без `wiki/.kit-version`)

1. `init` — создаст недостающее (`wiki/RULES.md`), существующее не тронет, поставит отметку версии.
2. `sync --dry-run` — покажет `CLAUDE.md` и шаблоны как конфликты: «что изменили в проекте» относительно текущей версии кита.
3. `CLAUDE.md`: всё проектное (рабочие договорённости, прод-доступ, особые правила) — в
   `QUICK_REF.md` новой секцией; личные привычки владельца, общие для всех проектов, — в
   `~/.claude/CLAUDE.md`; общие улучшения — §upstream. Затем взять `CLAUDE.md` из кита.
4. `wiki/INDEX.md` — заготовка, sync её не перепишет, правится руками:
   - удалить секции, переехавшие в `RULES.md`: «Когда предлагать ADR» (кроме таблицы областей),
     «После задачи», «Принципы документирования»;
   - таблицу областей оставить секцией `## Области ADR`; проектные строки маршрутов (не из общего
     списка `RULES.md`) — секцией `## Проектные маршруты`;
   - в «Куда идти за чем» добавить строки `RULES.md` и «Как прогнать регулярный процесс целиком» и
     секцию «Скиллы проекта» с таблицей (форма — `template/wiki/INDEX.md`), перенеся туда скиллы
     из `.claude/skills/`, если они есть; ссылки `INDEX.md §Когда предлагать ADR /
     §После задачи / §Принципы документирования` по вики заменить на `RULES.md §…`.
5. `stamp`, затем `status` — все файлы ядра «как в ките».
6. Показать владельцу diff миграции целиком до коммита.

## upstream — улучшение из проекта в кит

Улучшение протокола, шаблонов, ролей или общих скиллов, нужное всем проектам, не правится на месте
в проекте (`CLAUDE.md §Протокол агента`), а предлагается в кит.

1. Сформулировать: что меняется, почему, на каком прецеденте (проект, задача). Без прецедента —
   не предлагать: кит растёт из живых проектов, а не из идей.
2. `python <каталог-кита>/kit/kit.py status --project <корень>` — какие файлы ядра в проекте правили.
3. Получить одобрение владельца на формулировку.
4. В клоне кита — ветка, правка в `template/` (файлы проекта) или `plugin/` (роли и скиллы):
   - запись в `CHANGELOG.md`;
   - версия в `kit/VERSION`: patch — формулировки; minor — новое правило, роль, скилл;
     major — изменение структуры, требующее миграции в проектах (с инструкцией в CHANGELOG).
5. Коммит и push ветки; PR, если есть `gh` и права, иначе — показать владельцу diff и команду.
   Пушить в `main` — только по явному слову владельца.
6. После слияния: роли и скиллы доедут сами (плагин обновляется по коммиту); файлы проекта — `sync`
   в каждом проекте, когда в нём работают.
