# Установка и обновление кита — для агента

Любой агент с shell и git выполняет эти процедуры сам; плагин `agent-wiki` (`/agent-wiki:init`, `sync`, `upstream`) — удобство, не условие. Кит — файлы проекта (`template/` по `kit/MANIFEST`: `core` — ядро, `seed` — заготовки) и плагин `plugin/` (роли и скиллы; ставится на аккаунт, в проект не копируется). Ничего не коммитить без согласия владельца.

## Получить кит

Нужен **полный** клон — `sync` берёт прошлую версию ядра из истории:

```bash
git clone https://github.com/xkdg/agent-wiki-template <кит>                                   # первый раз
git -C <кит> fetch origin && git -C <кит> checkout --detach origin/main                        # обновить
```

Скрипт ставит версию текущего `HEAD` клона, другую — `--ref <коммит|тег>`. Python 3.8+ (`python` или `python3`).

## init — новый проект

1. Есть `wiki/.kit-version` — проект развёрнут, нужен `sync`. Есть `CLAUDE.md` или `wiki/` без отметки — §Миграция.
2. `python <кит>/kit/kit.py init --project <корень>` — создаёт файлы из `MANIFEST`, существующие не трогает, пишет `wiki/.kit-version`.
3. Заготовки — с владельцем, не выдумывая: черновик `INDEX §Проект` и `§Карта кода` по коду и README → показать; инварианты `QUICK_REF §Границы` называет владелец, из кода — только кандидаты; правая колонка `§Области ADR` — под проект. Пустой проект — подсказки остаются до первой задачи.
4. Сказать, что `CLAUDE.md` подтянет вики в следующей сессии или после `/clear`.

## sync — обновить ядро

1. `python <кит>/kit/kit.py sync --project <корень> --dry-run`, затем без `--dry-run`. Для каждого файла ядра скрипт сравнивает базу (версия кита проекта), проект и новый кит: не правили в проекте — обновляет; правили — **конфликт**, печатает оба diff и не сдвигает версию. Заготовки не трогает; отсутствующие новые — создаёт.
2. Конфликтов нет — версия сдвинута. Есть — §Конфликты.
3. Владельцу: что обновилось, какие конфликты и как разрешены, что из `CHANGELOG.md` касается проекта.

### Конфликты — решает владелец

- **Проектное в ядре** (прод, договорённости) — перенести в `QUICK_REF.md` (личное — в `~/.claude/CLAUDE.md`), взять версию кита.
- **Общее улучшение** — оставить и предложить в кит (§upstream); когда попадёт в кит, конфликт уйдёт сам.
- **Устаревшая правка** — взять версию кита.

Взять версию кита: `python <кит>/kit/kit.py take --project <корень> --path <файл> --ref <коммит>` (CRLF сохраняется, `--path` повторяемый). Все разрешены — `stamp` с коммитом, который напечатал sync.

## Миграция — проект на шаблоне 1.x (без `wiki/.kit-version`)

1. `init` — создаст недостающее (`wiki/RULES.md`), существующее не тронет, поставит отметку.
2. `sync --dry-run` — `CLAUDE.md` и шаблоны придут конфликтами относительно текущего кита.
3. `CLAUDE.md`: проектное (договорённости, прод-доступ) — новой секцией в `QUICK_REF.md`; личное — в `~/.claude/CLAUDE.md`; общие улучшения — §upstream. Затем `take` для `CLAUDE.md` и шаблонов.
4. `wiki/INDEX.md` правится руками (это заготовка):
   - удалить переехавшее в `RULES.md` — «Когда предлагать ADR» (кроме таблицы областей), «После задачи», «Принципы документирования»;
   - таблицу областей — секцией `## Области ADR`, проектные маршруты (не из `RULES.md`) — `## Проектные маршруты`;
   - в «Куда идти за чем» — строки `RULES.md` и «Как прогнать регулярный процесс целиком»; секция «Скиллы проекта» с таблицей (форма — `template/wiki/INDEX.md`) и скиллами из `.claude/skills/`;
   - ссылки `INDEX.md §Когда предлагать ADR / §После задачи / §Принципы документирования` по вики — на `RULES.md §…`.
5. `stamp`, `status` — все файлы ядра «как в ките». Показать владельцу полный diff миграции.

## upstream — улучшение из проекта в кит

Ядро в проекте не правится; улучшение для всех проектов предлагается в кит.

1. Что меняется, почему, на каком прецеденте. Без прецедента в проекте — не предлагать.
2. `kit.py status --project <корень>` — какие файлы ядра правили в проекте. Проектное отделить.
3. Одобрение владельца на формулировку.
4. В клоне кита — ветка; правка в `template/` (файлы проекта) или `plugin/` (роли, скиллы); запись в `CHANGELOG.md`; `kit/VERSION`: patch — формулировки, minor — новое правило, роль, скилл, major — структура с миграцией (инструкция — в CHANGELOG). Менялись роли, скиллы, манифесты — `claude plugin validate <кит>`.
5. Коммит, push ветки, PR (`gh`, если есть права; иначе — diff и команды владельцу). В `main` — только по слову владельца.
6. После слияния роли и скиллы обновятся сами (плагин версионируется коммитом); файлы проекта — `sync`.
