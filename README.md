# Agent Wiki Template

Шаблон инфраструктуры документации для AI-агента (Claude Code / Cursor / любой LLM-агент с file-tools) в кодовом проекте.

Идея: дать агенту не «свободу импровизации в большом контексте», а **узкий протокол** — что читать перед задачей, какой жанр документа для какого типа знания, что делать с документацией после задачи. Каждый артефакт играет одну роль, не пересекается с другими, имеет понятное время жизни.

---

## Что внутри

```
agent-wiki-template/
├── README.md                       ← этот файл
├── CLAUDE.md                       ← универсальный протокол агента (копируется в корень нового репо ~as-is)
└── wiki/
    ├── INDEX.md                    ← точка входа: «что за проект», куда идти за чем, гейт ADR, роутинг после задачи
    ├── context/
    │   ├── QUICK_REF.md           ← cheat sheet, читается на каждой задаче
    │   ├── PRODUCT.md             ← бизнес-описание: процессы, интеграции, данные (mermaid-схемы)
    │   └── CONVENTIONS.md         ← правила реализации с прецедентом (C-NN)
    ├── adr/
    │   └── _TEMPLATE.md           ← шаблон ADR (00NN-<тема>.md)
    └── todo/
        ├── _TEMPLATE.md           ← шаблон ТЗ
        └── BACKLOG.md             ← планируемое
```

## Жанровая граница (важно)

Каждый артефакт = одна роль. Не пересекаются, не дублируются.

| Артефакт | Жанр | Что попадает | Время жизни |
|---|---|---|---|
| **CLAUDE.md** | Протокол агента | Что читать до задачи, четыре состояния `documentation_action` после, подход к работе, субагенты, когда заводить ТЗ | Постоянно |
| **INDEX.md** | Точка входа в проект | Что за проект, куда идти за чем, карта кода, гейт «когда предлагать ADR», роутинг `documentation_action` | Долго, обновляется по мере роста |
| **QUICK_REF.md** | Cheat sheet | Границы-инварианты + state machine, формулы, пороги, контракты данных — то, что нужно на каждой задаче | Долго, апдейтится при изменении инвариантов |
| **PRODUCT.md** | Бизнес-описание (BABOK RADD-модели) | Продукт, акторы (C4 L1), процессы (flowchart), интеграции (sequence), данные (ER) — схема первична | Долго |
| **CONVENTIONS.md** | Правила реализации | Правило + прецедент, из которого оно выведено (`C-NN`) | Долго |
| **ADR** | Прескриптивное решение | Контекст → решение → альтернативы → последствия. Принимается **до или вместе** с реализацией | Постоянно. Заменяется новым ADR через `Supersedes`; списывается вместе со своим номером |
| **BACKLOG.md** | Намерения | Что планируем сделать и по какому признаку это будет сделано | Долго |
| **todo/<task>.md** | ТЗ | Декомпозиция конкретной задачи. После `done` — амортизируется и удаляется | Короткое (живёт одну задачу) |

**Принцип амортизации:** документ живёт, пока его содержимое не переехало в долговечное место. Переехало — исходный удаляется: две копии расходятся, и вторая начинает врать.

**Принцип единственного источника истины:** каждый факт живёт в одном месте; смежный документ на него ссылается, а не пересказывает. Дубль текста = долг.

**Реестра долгов нет.** Найденная проблема либо чинится на месте, либо называется в финале ответа; пункт бэклога заводится по одобрению. Отдельного списка «с чем живём» не бывает — архив, который никто не разгребает, начинает врать. Принятый компромисс описывается в «Последствиях» того ADR, который его породил, вместе с ценой.

**Правило, которое можно проверить машиной, проверяется машиной.** Тест, тип, схема или линтер вместо записи в вики; текстовое правило — когда автоматизировать нечем, и тогда оно ссылается на механизм, а не пересказывает его.

## Ядро протокола: `documentation_action`

Главное, чем этот шаблон отличается от «просто набора md-файлов»: после задачи агент **не обновляет документацию по умолчанию**. Умолчание — `none`, и обычная задача документацию не меняет. Всего состояний четыре:

| Состояние | Когда |
|---|---|
| `none` | умолчание |
| `update_existing` | документ утверждает то, что стало неверным. Правка точечная, на месте, нового жанра не заводит |
| `propose_new` | есть основание для нового долгоживущего артефакта: агент называет его в финале — тип, тема, основание, рекомендация. **Не создаёт** |
| `create_approved` | владелец продукта попросил или одобрил предложение |

**Различие, на котором всё держится: неверное утверждение чинится, новое знание называется.** Без явного одобрения не заводятся ADR, `C-NN`, новые страницы вики и пункты бэклога — иначе вики распухает от записей, которые никто не перечитывает, и через полгода врёт в деталях.

Расхождение документа с кодом — `update_existing` независимо от того, в этой ли задаче оно возникло: чтение вики перед задачей и есть механизм, которым расхождения ловятся. Прав при этом не всегда документ: неверен код — состояние `none`, чинится код.

## Как использовать в новом проекте

1. Скопировать содержимое `agent-wiki-template/` в корень нового репо:
   ```
   cp agent-wiki-template/CLAUDE.md  <new-project>/
   cp -r agent-wiki-template/wiki    <new-project>/
   ```
   (`README.md` копировать не нужно — это про сам шаблон)

2. **CLAUDE.md** — оставить как есть. Это универсальный протокол агента; конкретику он смотрит в `wiki/INDEX.md`.

3. **wiki/INDEX.md** — заполнить под проект: что за проект и ключевые развилки; карту кода; правую колонку таблицы областей в `§Когда предлагать ADR`; проектные строки роутинга в `§После задачи`. Секции «Куда идти за чем» и «Принципы документирования» переносятся почти как есть — они про жанры, а не про проект.

4. **wiki/context/QUICK_REF.md** — заполнить `§Границы` (инварианты, изменение — повод предложить ADR) и факты: state machine, пороги, формулы, контракты данных. Только то, что нужно на каждой задаче.

5. **wiki/context/PRODUCT.md** — бизнес-описание: контур акторов (C4 L1), процессы flowchart'ами, интеграции (таблица + sequence), данные (ER + словарь сущностей).

6. **CONVENTIONS.md / BACKLOG.md** — стартуют пустыми, наполняются по мере работы и только по одобрению.

7. **adr/_TEMPLATE.md / todo/_TEMPLATE.md** — шаблоны на копирование, удалять не нужно.

## Идеология

Протокол агента (`CLAUDE.md`) стоит на принципах «думать до кода · минимум кода · хирургические правки · проверяемые критерии · корректность до оптимизации · зелёные тесты не приёмка», а wiki замыкает цикл: агент знает, **что именно** читать перед задачей и **что именно** делать с документацией после — включая законный ответ «ничего». Нумерация и форматы записей — в шапках самих файлов; сквозные принципы документирования — в `INDEX.md §Принципы документирования`.

Проверено в бою на нескольких проектах; изменения приезжают обратно инкрементом из живой вики, а не придумываются в шаблоне.
