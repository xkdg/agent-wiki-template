# CLAUDE.md

Стартовый промпт агента. Не содержит проектных фактов — конкретика в `wiki/INDEX.md`.

---

## Протокол агента

**Перед каждой задачей читать:**
1. `wiki/INDEX.md` — что за проект, карта wiki «куда идти за чем», чек-лист значимости и матрица документации
2. `wiki/context/QUICK_REF.md` — оперативные факты и границы-инварианты (state machine, формулы, пороги)

Остальная документация (бизнес-описание продукта, ADR, конвенции) — по роутингу из INDEX, когда нужна.

**После каждой задачи — две независимые проверки** (объём правки не критерий: однострочная правка может быть архитектурно значимой):
1. Чек-лист значимости — `wiki/INDEX.md §Архитектурно значимое`. Хоть один пункт `да` → обновить документацию по матрице `wiki/INDEX.md §После задачи`.
2. Если задача велась по ТЗ-файлу — отметить `[x]` выполненные пункты, обновить статус; полностью `done` с подтверждённой приёмкой → амортизировать и удалить ТЗ по чек-листу `§Амортизация` в самом файле.

## Подход к работе

1. **Думать до кода.** Несколько интерпретаций — озвучить, не выбирать молча. Видишь решение проще — сказать и обосновать. Непонятно — остановиться и спросить.
2. **Минимум кода.** Только то, что закрывает задачу. Без абстракций под единственный use-case, без error-handling невозможных сценариев. Написал 200 строк, а можно 50 — переписать.
3. **Хирургические правки.** Каждая изменённая строка трассируется к запросу. Не улучшать соседний код, не рефакторить работающее, не удалять предсуществующий мёртвый код без просьбы. Держаться стиля файла.
4. **Цель с проверяемым критерием.** Не «исправить баг», а «тест, воспроизводящий баг, зелёный». Для многошаговых задач — краткий план с чек-поинтами.
5. **Не замалчивать.** Блокер — назвать его и варианты обхода. Попутные проблемы вне задачи — упомянуть в финале, не править молча.

## Субагенты

- **Мощность модели — под сложность задачи** (экономия токенов): лёгкая механика по чёткой пошаговой инструкции → слабая/дешёвая модель; ресёрч, сборка по готовой спецификации, разведка кодовой базы → средняя; отладка, неочевидные зависимости, высокая цена ошибки → сильная. Не уверен — модель не указывать (наследуется модель сессии).
- **Спецификация агенту самодостаточна:** точные пути и форматы, что прочитать перед работой, границы «что в / что вне», критерии самопроверки (ассерты, контрольные числа) — агент проверяет свой результат и отчитывается о проверке, а не только «делает».
- **Параллелизм:** независимые задачи — параллельными агентами в одном сообщении, зависимые — последовательно. Не дублировать работу запущенного агента своими руками.

## ТЗ-файл

**Когда заводить** `wiki/todo/<short-kebab-name>.md` (шаблон, границы и формат — `wiki/todo/_TEMPLATE.md`):
- задача больше пары часов или требует декомпозиции на шаги
- скоуп нечёткий — зафиксировать «что в / что вне» до старта
- нужно согласование подхода до реализации

ТЗ-файл и обновление документации — независимые оси: маленькая правка может быть значимой и требовать обновления вики без ТЗ, а большое ТЗ — не трогать архитектуру.
