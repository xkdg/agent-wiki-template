## Контекст

*2–5 предложений: откуда задача, что без неё плохо, какая боль закрывается. Достаточно, чтобы понять «зачем» без открытия других файлов.*

*Пример:*

*В deep-crawl есть retry-механизм по `deep_crawl_retry_after`, но нет способа явно переоткрыть записи, упавшие с ошибкой, без ожидания backoff. На проде после деплоя фикса нужно вручную пересмотреть ~50 записей с `deep_crawl_done=FALSE` и неправильным `error_code`. Аналог `--retry-errors` уже есть в aiohttp-crawl и закрывает похожий кейс.*

### В рамках задачи

- *По флагу — селектор сбрасывает `deep_crawl_retry_after = NULL` для записей с `deep_crawl_done=FALSE AND error_code IS NOT NULL`*
- *Логирование сколько записей переоткрыто*

### НЕ входит (явно отклонено из скоупа)

*Что искушение тащить, но не тащим. Главная защита от scope creep.*

- *Не меняем логику самого retry-gate — только сбрасываем backoff*
- *Не добавляем фильтр по конкретному `error_code` — переоткрываем все*
