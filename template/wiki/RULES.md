# Правила документации

> Ядро agent-wiki-template: одинаково во всех проектах, в проекте не правится (`CLAUDE.md §Протокол агента`). Проектная часть тех же правил — `INDEX.md §Области ADR` и `§Проектные маршруты`.

---

## Когда предлагать ADR

Только предложение: ADR заводится после явного одобрения. Объём правки не критерий — однострочная правка бывает значимой, а рефакторинг на тысячу строк — нет.

**Все четыре условия сразу:**
1. принято долговечное решение, а не просто выполнена задача;
2. есть минимум две реалистичные альтернативы, и отвергнутая отсечена названным критерием;
3. решение влияет шире собственной реализации;
4. мотивация неочевидна из кода, тестов и конфигурации.

**И задета хотя бы одна область** — state machine, схема БД, контракт API / CLI, протокол между компонентами, конфиги / пороги / формулы, инвариант `QUICK_REF §Границы`, cross-cutting, стоимость; признаки в этом проекте — `INDEX.md §Области ADR`.

**ADR не заводится** для bug fix, локального рефакторинга, имени файла или функции, поля по существующему паттерну, реализации уже принятого решения, восстановления прежнего поведения, настройки библиотеки внутри выбранного стека и решения, целиком читаемого из публичного контракта и тестов.

---

## Когда предлагать скилл

Скилл — повторяемый процесс: последовательность шагов и ловушки, из-за которых порядок именно такой. Вики — факты и решения, роль субагента — кто исполняет. Скилл не дублирует числа, пороги и state machine — ссылается на вики. Только предложение, создаётся по одобрению.

**Все условия сразу:**
1. процесс прогнан минимум второй раз (повтор — факт, а не прогноз) или владелец назвал его регулярным;
2. его порядок не выводится из кода за разумное время: шаги зависят друг от друга, есть ловушки, необратимые операции или ручная приёмка;
3. процесс не сводится к одному скрипту — иначе нужен скрипт, а не скилл.

**Форма** — `.claude/skills/<kebab-name>/SKILL.md`. `description` — что делает и все формулировки, которыми о процессе просят, с оговоркой «даже если слово „скилл“ не звучит»: скилл находится только по нему. Секции: «Перед стартом прочитать» (ссылки на вики, не пересказ) · «Критерии приёмки владельца» (с датой фиксации) · «Последовательность» · «Ловушки» (каждая — с тем, чего стоила) · «Что писать в отчёт». Есть соседние задачи с похожей лексикой — `evals/trigger-eval.json`: половина запросов должна вызывать скилл, половина — near-miss, не должна.

Процесс изменился или на ловушку наступили заново — `update_existing` скилла. Новый скилл вносится в таблицу скиллов `INDEX.md`. Скилл, нужный во всех проектах, — предложение в кит, а не `.claude/skills/` проекта.

## После задачи — `documentation_action`

Состояния — `CLAUDE.md §Протокол агента`. Ниже общие маршруты, проектные — `INDEX.md §Проектные маршруты`; чего нет ни там, ни здесь — `none`.

| Что произошло | Действие |
|---|---|
| Изменено число, статус, формула или контракт из `QUICK_REF` | `update_existing`: `QUICK_REF` |
| Изменён процесс, интеграция или схема данных из `PRODUCT` | `update_existing`: `PRODUCT` — секция и её диаграмма |
| Изменён контракт команды или эндпоинта из `README` | `update_existing`: `README` |
| Появилась подсистема или сменился канонический источник | `update_existing`: таблица подсистем `INDEX` |
| Изменён инвариант `QUICK_REF §Границы` | **оба сразу:** `update_existing` `QUICK_REF` (иначе файл, читаемый на каждой задаче, врёт) и `propose_new`: ADR со строкой `Supersedes` |
| Прошёл gate `§Когда предлагать ADR` | `propose_new`: ADR |
| Приём или дефект — в двух независимых местах либо однажды дорого | `propose_new`: `C-NN` — при остальных условиях шапки `CONVENTIONS.md` |
| Прошёл gate `§Когда предлагать скилл` | `propose_new`: скилл |
| Изменился процесс скилла или на его ловушку наступили заново | `update_existing`: `.claude/skills/<name>/SKILL.md` |
| Улучшение протокола, шаблонов, ролей или общих скиллов для всех проектов | `propose_new`: изменение кита → `/agent-wiki:upstream` |
| Сознательный костыль остаётся жить | назвать в финале; **границу, которую он держит, — `update_existing` `QUICK_REF`** |
| Попутная находка, идея, отложенная проблема | назвать в финале; `BACKLOG` и вики не трогать |
| Задача велась по ТЗ | `[x]` и статус в файле; `done` + подтверждённая приёмка → амортизация и удаление |

## Принципы документирования

- **Амортизация.** Документ живёт, пока его содержимое не переехало в долговечное место; переехало — исходный удаляется, иначе две копии разойдутся.
- **Единственный источник истины.** Факт живёт в одном месте, остальные ссылаются, а не пересказывают.
- **Ссылки — по необходимости:** там, где без них теряется контекст; отсутствие ссылки — не дефект. Секций связей и обратных ссылок нет — граф, который поддерживают руками, устаревает первым.
- **Проверяемое машиной проверяется машиной:** тест, тип, схема, линтер вместо записи в вики; запись тогда ссылается на механизм.
- **Реестра долгов нет.** Проблема чинится на месте или называется в финале; пункт `BACKLOG` — по одобрению. Принятый компромисс — в «Последствиях» породившего его ADR, с ценой.
- **Нумерация** `ADR-00NN` и `C-NN` — sequential, номера **никогда не переиспользуются**.
- **Ссылки на смертное.** На ТЗ-файлы из ADR, `CONVENTIONS`, `PRODUCT`, `QUICK_REF` не ссылаться — кроме ТЗ, помеченных постоянными в `INDEX`.
